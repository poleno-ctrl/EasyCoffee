# Contributing Guidelines

Спасибо, что хотите внести вклад в проект! Пожалуйста, ознакомьтесь с основными правилами, чтобы процесс разработки оставался единообразным и удобным для всей команды.

---

## Ветвление

В проекте используется структура веток по типам задач.  
Все ветки создаются от `develop`.

| Тип ветки | Назначение | Пример |
|------------|-------------|--------|
| `feature/` | Новая функциональность | `feature/add-user-profile` |
| `bugfix/` | Исправление ошибок, найденных в процессе разработки | `bugfix/fix-login-validation` |
| `refactor/` | Рефакторинг без изменения логики работы | `refactor/optimize-database-layer` |
| `release/` | Подготовка очередного релиза | `release/1.3.0` |
| `launch/` | Создание и настройка репозитория | `launch/1.1.0` |

**Основные ветки:**
- `main` — стабильная версия проекта (релизы)
- `develop` — основная ветка разработки, куда мержатся все изменения после ревью

---

## Стиль коммитов

Все коммиты должны соответствовать соглашению [Conventional Commits](https://www.conventionalcommits.org/).

#### Примеры:
- `feat(auth): add password recovery`
- `fix(ui): correct button alignment on settings screen`
- `refactor(repo): simplify caching logic`
- `docs(readme): update installation section`
- `test(api): add tests for error handling`

#### Допустимые типы:
| Тип | Назначение |
|------|-------------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибок |
| `refactor` | Рефакторинг без изменения поведения |
| `docs` | Изменения в документации |
| `test` | Добавление или изменение тестов |
| `chore` | Рутинные задачи (обновление зависимостей, конфигурации и т.п.) |
| `build` | Изменения, влияющие на сборку проекта |
| `ci` | Изменения в конфигурации CI/CD |

**Рекомендации:**
- Сообщения коммитов должны быть **на английском языке**.
- Используйте **повелительное наклонение** (например: `add`, `fix`, `update`).
- Не ставьте точку в конце строки.
- Один коммит — одно логическое изменение.

---

## Система Approve’ов

Перед слиянием ветки в `develop` необходимо получить **approve от трех участников команды**.

**Правила:**
1. Каждый Pull Request должен проходить **code review**.
2. Мерж возможен **только после тремя участниками команды**.
3. Если изменения затрагивают архитектуру или критические части системы — обсуждение обязательно перед созданием PR.
4. Самостоятельное слияние без ревью **запрещено**.

---

##  Общие рекомендации

- Поддерживайте чистую историю коммитов: по возможности используйте `rebase` перед merge.
- Не коммитьте сгенерированные файлы или временные данные (всё должно быть добавлено в `.gitignore`).
- Проверяйте, что код компилируется и проходит все тесты перед созданием PR.
